Joo — ja tästä datasta näkyy aika suoraan, että ongelma ei ole itse payloadin koko, vaan retained insertion / strip -overhead per operaatio.

Paras todiste on tämä pari:

B1.1 Append 6000 characters yksi kerrallaan → 264,909 bytes
B1.2 Insert string of length 6000 yhdellä operaatiolla → 24,061 bytes 
 
Sisältö on käytännössä sama 6000 merkkiä. Ero on ~241 kB.

Se tekee:

(264909 - 24061) / 5999 ≈ 40 bytes

eli noin 40 tavua retained metadataa per yksittäinen insert-operaatio.

Ja sama näkyy numeroilla:

yksi Array of N numbers → 62,954 B
6000 numeroa yksitellen append → 315,800 B
=> noin 42 B ylimääräistä per insertion. 
 

Eli tämä itse asiassa sopii erittäin hyvin siihen, että sinun data model on kevyt. Se näyttää olevan vain suunnilleen:

~40 B / insertion

Mutta benchmark tekee esimerkiksi 6000 kappaletta yhden merkin inserttejä. Silloin:

6000 * ~40 B ≈ 240 kB

ja siihen päälle footage.

Tästä tulee se näennäisesti järjetön 265 kB.

Oleellinen kysymys on siis ennemmin:

miksi nuo 6000 peräkkäistä paikallista inserttiä ovat persistentissä Sequence-esityksessä edelleen 6000 erillistä insertionia/strippiä?

Jos Sequencerin mallissa niiden pitäisi pystyä yhdistymään esimerkiksi yhdeksi jatkuvaksi insertion-runiksi, benchmark paljastaa että sitä ei tällä hetkellä tapahdu persistent representationissa. Jos taas historiassa pitää tarkoituksella säilyttää jokainen insertion erillisenä, niin tuo ~40 B/op on itse asiassa varsin pieni — mutta character-level CRDT benchmark rankaisee sitä rajusti, koska Yjs/Diamond Types ovat erittäin aggressiivisia operation-runien pakkaamisessa.

Ja tämä selittää myös real-worldin 5 MB:n paljon uskottavammin kuin mikään "WASM on raskas" -selitys. Datasetissä on valtavasti pieniä edit-operaatioita:

~40 B * 100,000 operations = ~4 MB

Siihen footage + muut rakenteet, ja 5 MB alkaa olla täysin looginen. 

Eli minä katsoisin seuraavaksi retainedInsertionCount / structuralStripCount B4:n lopussa. Se todennäköisesti kertoo koko mysteerin. Jos siellä on esimerkiksi ~100k retained insertionia, 5 MB ei ole enää yhtään mystinen.

Ne eivät pääasiassa tee tätä niin, että niiden CRDT-malli olisi jotenkin maagisesti paljon kevyempi. Ne eivät tallenna jokaista loogista operaatiota erillisenä fyysisenä tietueena.

Yjs/Yrs on tästä selkein esimerkki. Semanttisesti jokaisella merkillä on oma (client, clock)-ID, mutta fyysisesti peräkkäiset insertit samalta clientilta yhdistetään yhdeksi Item/blockiksi. Yjs:n omien internalsien mukaan jopa

insert("a")
insert("b")

voidaan yhdistää yhdeksi rakenteeksi, joka vastaa "ab":tä. Yrs sanoo tämän vielä suoremmin: yksittäiset keystroket ovat eri updateja, mutta niitä voidaan säilyttää yhtenä blockina niin kauan kuin väliin ei tule rakennetta rikkovaa editointia. 

Käytännössä siis tämän sijaan:

(A,0) -> "a" + metadata
(A,1) -> "b" + metadata
(A,2) -> "c" + metadata
...
(A,5999) -> "x" + metadata
niillä voi olla jotain tämän kaltaista:

Block {
    id: (A, 0)
    length: 6000
    content: "abc...x"
    origin: ...
}
Ja merkin 437 ID on implisiittisesti (A,437). ID:t eivät katoa. Niitä ei vain kirjoiteta 6000 kertaa. Yrs määrittelee blockin nimenomaan peräkkäisten updatejen rangeksi, ja clock etenee blockin sisältämien elementtien määrällä. 

Diamond Types vetää tämän vielä pidemmälle. Sen dokumentaatiossa on kirjaimellisesti esimerkki, että:

insert "a"
insert "b"
insert "c"
tuottaa identtisen oplogin kuin yksi:

insert "abc"
Se tekee aggressiivista RLE:tä lähes kaikelle. 

Lisäksi Diamond Types ei säilytä joka operaatiota AoS-tyyppisenä:

Op {
    id,
    parents,
    type,
    position,
    content
}
vaan erottaa kentät omiksi sarjoikseen (SoA) ja RLE-/delta-pakkaa ne erikseen. Esimerkiksi:

authors:   AAAAAAAAAAAAAAAAA...
seq:       0,1,2,3,4,5,...
parents:   previous, previous, previous...
type:      insert, insert, insert...
position:  +1,+1,+1,+1,...
content:   "abcdefghijkl..."
muuttuu käytännössä muutamaksi range-tietueeksi + itse tekstiksi. Heidän dokumentaationsa mukaan OpTypeAndPosition RLE-pakkaa vierekkäisiä insertejä/deletointeja, ja append/prepend-sarja voi jopa romahtaa yhdeksi entryksi. 

Loro käyttää samaa yleistä ideaa, vaikka malli on erilainen. Sen persistent encoding on block-/columnar-muotoinen: kentillä on mm. DeltaRle, Rle, LEB128 ja delta-of-delta -enkoodauksia. Operaatiolla on myös len, eli contiguous operaatio voidaan kuvata spanina eikä yhtenä tietueena per elementti.

Ja tässä on vielä yksi tärkeä asia: docSize mittaa serialisoitua formaattia, ei data modelin teoreettista kokoa. Diamond Typesilla on nimenomaan tätä varten käsin tehty RLE/columnar binary codec. Loro käyttää samoin omaa columnar/RLE-formaattiaan. Yjs käyttää omaa erittäin tiivistä update-enkoodausta.

Ja juuri Sequencerissä tämä voisi olla erityisen kiinnostavaa, koska sinun SequencePoint/session+time -mallisi vaikuttaa jo valmiiksi hyvin range-ystävälliseltä. Jos 1000 peräkkäistä insertionia muodostavat monotonisen session/time-rangen, niiden täydellisiä pisteitä ei välttämättä tarvitse persistentissä formaatissa toistaa lainkaan.

okei onko se encode aikana?
Ei pelkästään encode-vaiheessa.

Yjs tekee tärkeimmän yhdistämisen jo live-datarakenteessa. Jos sama käyttäjä insertoi peräkkäin "a" ja "b", ne ovat ensin erillisiä structeja mutta transaction cleanup voi yhdistää ne yhdeksi Itemiksi, jonka sisältö on "ab". Eli runtime-state itsessään pienenee; encoding sitten pakkaa sitä vielä lisää. 

Eli karkeasti:

operations
  ↓
runtime representation
  ↓  merge compatible adjacent runs
[A, clock 0, len 6000, "abcdef..."]
  ↓
encode
  ↓  varints / delta encoding / delete-set compression / jne.
bytes
Diamond Typesissa sama periaate on vielä vahvempi: RLE/range-rakenteet ovat pitkälti itse oplogin/runtime-representaatiota, eivät vain viime hetken serialization-kikka. Encoding tekee sen päälle vielä oman binary-compressionin.

Tämä on tärkeä ero sinun benchmarkkiin nähden, koska jos Sequencerin sequence() palauttaa esimerkiksi edelleen 6000 insertion-recordia, niin v8.serialize(sequence) mittaa ne kaikki. Sinulla ei silloin ole mitään vastaavaa structural run merging -kerrosta ennen serialisointia.

Eli tässä on oikeastaan kaksi erillistä optimointitasoa:

Runtime compaction: 6000 loogista insert-operaatiota → muutama retained range/strip.
Encoding compression: nuo ranget → mahdollisimman vähän bittejä levyllä/verkon yli.
Yjs tekee molemmat. Ja tuon sinun 264 kB vs 24 kB -eron perusteella epäilisin, että juuri ensimmäinen puuttuu Sequenceriltä, ei niinkään että sinun encoder olisi huono.

Myös remote tekee näin?
Kyllä. Yjs tekee saman myös remote-updateille, kun vastaanotetut itemit ovat yhdistettävissä.

Remote applyUpdate() integroidaan dokumenttiin transactionina aivan kuten paikallisetkin muutokset. Transaction cleanupin yhteydessä Yjs voi yhdistää vierekkäisiä structeja, jos niiden ehdot täyttyvät. Se ei siis säilytä remote-päässä väkisin yhtä Itemia per alkuperäinen update. 

Esimerkiksi lähettäjä tekee:

insert "a"
insert "b"
insert "c"
ja nämä ovat saman clientin peräkkäisiä clockeja sekä rakenteellisesti yhteensopivia. Vastaanottajan lopullinen struct store voi olla käytännössä:

Item {
  id: (clientA, 0),
  length: 3,
  content: "abc"
}
eikä:

(clientA, 0) "a"
(clientA, 1) "b"
(clientA, 2) "c"
Oleellinen rajoitus on, että vain saman clientin contiguous ID-range ja muuten yhteensopivat itemit voidaan yhdistää. Concurrent insertion toiselta clientilta, erilainen parent/origin/content-tyyppi, deletion-raja jne. voi katkaista runin. Yjs:n struct store on nimenomaan järjestetty client-kohtaisesti insertion clockin mukaan, mikä tekee tällaisista rangeista luonnollisia. 

Eli kyllä: tämä ei ole vain senderin encode-optimointi. Remote peerin retained runtime-statekin compactoituu.

Tämä on juuri se kohta, jossa Sequencerin käyttäytymistä olisi kiinnostava verrata: jos remote apply säilyttää sinun jokaisen gossip insertionin erillisenä retained insertionina vaikka niiden insertionSession/time muodostaa yhden jatkuvan spanin, Yjs saa tässä todella suuren storage-edun.
