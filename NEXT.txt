Tästä benchmarkista näkyy aika selkeästi, missä ongelma tällä hetkellä on.

Scale-up näyttää vielä järkevältä. 0 → 10k Stripin workloadissa keskimääräiset ajat ovat tail insert ~15 µs, random find ~32 µs, random remove ~83 µs, random replace ~95 µs, random insert ~60 µs ja peer ingest ~133 µs. Testi on Node 24.16 / V8 13.6:lla i5-10210U:lla, 3 ajoa, Strip-pituus 1–100 Framea.

Varsinainen punainen lippu on historian retainaus scale-downissa. Kun näkyviä Stripejä on lopulta 0, jäljelle jää edelleen noin 121–123k retained Deltaa, noin 21.4–21.5 MB arvioitua replica-muistia ja noin 3.89–3.93 MB snapshot-dataa. Käytännössä snapshot on erittäin tasaisesti noin 32 B per retained Delta, ja runtime-estimaatti noin 174–177 B per retained Delta.

Tämä selittää myös sen, miksi create alkaa räjähtää. Run 0:ssa create on 10k Stripin scale-up snapshotista ~1.63 s, mutta kun dokumentti on scale-downissa enää 1k näkyvää Stripiä, create kestää jo 6.72 s. Eli kustannus ei seuraa live-dokumentin kokoa vaan retained historya.

Sama näkyy operaatioissa: scale-downissa head/tail remove ovat ~2.56 ms/op ja random find ~832 µs/op, vaikka live-rakenne pienenee. Tässä pitää kuitenkin huomata, että scaling-taulukon checkpoint-luvut ovat kumulatiivisia lifecycle-averageja, eivät sen hetkisen koon puhtaita latencyja. Eli niistä ei saa päätellä esimerkiksi, että 100 Stripin todellinen find olisi juuri taulukon ilmoittama arvo.

Muistin B/Strip scale-downissa on siksi myös harhaanjohtava mittari: kun denominator menee kohti nollaa mutta historia jää, päädytään miljooniin tavuihin per näkyvä Strip. Benchmarkin omat full-lifecycle-luvut näyttävät ~9.4 kB/Strip ja ~186 B/Frame, mutta nämä yhdistävät kaksi täysin eri tilaa. Paremmat seurattavat luvut olisivat erikseen live structural memory / visible Frame, history memory / retained Delta, snapshot bytes / retained Delta ja create time / retained Delta.

Eli tämän perusteella tärkein seuraava optimointikohde ei ole vielä yksittäinen find-mikro-optimointi vaan compaction/GC, koska nykyinen rakenne palautuu visuaalisesti 10k → 0 mutta ei tilallisesti takaisin kohti nollaa. Benchmark myös nimenomaan kertoo, että checkpointissa vanha replica tuhotaan ja luodaan snapshotista uudelleen, joten kyse ei ole vain vanhan JS-heapin jäämisestä roikkumaan.

Lyhyesti: live-rakenne skaalautuu vielä siedettävästi; retained history ei. Tämä benchmark on erittäin hyvä testi juuri compactionin vaikutuksen mittaamiseen.

## Measurement notes

- Scale is the number of visible logical Strips maintained by the benchmark model. Every mutation targets a complete Strip boundary; retained Mask structures are reported separately.

- The workload has two Replicas editing the same document. Local Mutations are ingested by the peer outside timed regions; randomIngest times the measured Replica consuming each atomic acknowledgement-plus-Delta packet from a peer replacement.

- Per-Replica bytes after automatic native collection and restart are an explicit estimate: four bytes per retained snapshot metadata word plus eight bytes per JavaScript Footage array slot. Process RSS is shared and reported at checkpoint scope; WebAssembly linear memory is unavailable through the public API.

- Persistent representation size is the byte length of node:v8.serialize over the automatically collected public snapshot.

- Every checkpoint explicitly destroys the old Replica and creates a fresh Replica from the automatically collected snapshot.

Sulje

Tästä benchmarkista näkyy aika selkeästi, missä ongelma tällä hetkellä on.

**Scale-up näyttää vielä järkevältä.** 0 → 10k Stripin workloadissa keskimääräiset ajat ovat tail insert ~15 µs, random find ~32 µs, random remove ~83 µs, random replace ~95 µs, random insert ~60 µs ja peer ingest ~133 µs.  Testi on Node 24.16 / V8 13.6:lla i5-10210U:lla, 3 ajoa, Strip-pituus 1–100 Framea. 

**Varsinainen punainen lippu on historian retainaus scale-downissa.** Kun näkyviä Stripejä on lopulta **0**, jäljelle jää edelleen noin **121–123k retained Deltaa**, noin **21.4–21.5 MB** arvioitua replica-muistia ja noin **3.89–3.93 MB snapshot-dataa**.    Käytännössä snapshot on erittäin tasaisesti noin **32 B per retained Delta**, ja runtime-estimaatti noin **174–177 B per retained Delta**.

Tämä selittää myös sen, miksi **create alkaa räjähtää**. Run 0:ssa create on 10k Stripin scale-up snapshotista ~1.63 s, mutta kun dokumentti on scale-downissa enää 1k näkyvää Stripiä, create kestää jo **6.72 s**.  Eli kustannus ei seuraa live-dokumentin kokoa vaan retained historya.

Sama näkyy operaatioissa: scale-downissa head/tail remove ovat ~2.56 ms/op ja random find ~832 µs/op, vaikka live-rakenne pienenee.  Tässä pitää kuitenkin huomata, että scaling-taulukon checkpoint-luvut ovat **kumulatiivisia lifecycle-averageja**, eivät sen hetkisen koon puhtaita latencyja.  Eli niistä ei saa päätellä esimerkiksi, että 100 Stripin todellinen find olisi juuri taulukon ilmoittama arvo.

Muistin `B/Strip` scale-downissa on siksi myös harhaanjohtava mittari: kun denominator menee kohti nollaa mutta historia jää, päädytään miljooniin tavuihin per näkyvä Strip. Benchmarkin omat full-lifecycle-luvut näyttävät ~9.4 kB/Strip ja ~186 B/Frame, mutta nämä yhdistävät kaksi täysin eri tilaa.  Paremmat seurattavat luvut olisivat erikseen **live structural memory / visible Frame**, **history memory / retained Delta**, **snapshot bytes / retained Delta** ja **create time / retained Delta**.

Eli tämän perusteella tärkein seuraava optimointikohde ei ole vielä yksittäinen `find`-mikro-optimointi vaan **compaction/GC**, koska nykyinen rakenne palautuu visuaalisesti 10k → 0 mutta ei tilallisesti takaisin kohti nollaa. Benchmark myös nimenomaan kertoo, että checkpointissa vanha replica tuhotaan ja luodaan snapshotista uudelleen, joten kyse ei ole vain vanhan JS-heapin jäämisestä roikkumaan. 

Lyhyesti: **live-rakenne skaalautuu vielä siedettävästi; retained history ei.** Tämä benchmark on erittäin hyvä testi juuri compactionin vaikutuksen mittaamiseen.
