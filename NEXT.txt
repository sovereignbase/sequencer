Nyt kun katsotaan **nykyistä masteria nimenomaan O(1)-vakiohinnan kannalta**, siellä on muutama aika selvä syyllinen. Suurin löytö on paljon pahempi kuin odotin.

1. **Jokainen update tekee tällä hetkellä native heap allocation + free -kierroksen vain palauttaakseen 12 sanaa.** `update_projection()` tekee `projection_buffer.resize(1)`, mutta TS:n `read_projection_from_buffer()` kutsuu lopuksi `_clear_projection_buffer()`. C++:n `ProjectionBuffer::clear()` ei tee tavallista `vector.clear()`ia vaan `std::vector<...>{}.swap(strips)`, eli **capacity vapautetaan kokonaan**. Seuraava yhden Stripin update joutuu taas allokoimaan 48 tavun bufferin. 

Tämä on ensimmäinen asia jonka korjaisin. `ProjectionBuffer::clear()` pitäisi tässä käyttötarkoituksessa olla käytännössä:

```cpp
strips.clear();
```

jolloin capacity jää eloon. Vielä parempi olisi erottaa yhden local-updaten tulos kokonaan omaksi fixed `std::array<uint32_t, 12>` -bufferiksi. Silloin ei tarvita `vector::resize()`ä ollenkaan.

2. **Sen native-allokaation päälle tulee JS-allokaatio joka ikisellä updatella.** Nykyinen lukija tekee:

```ts
Array.from(
  wasm.HEAPU32.subarray(start, start + 12)
)
```

eli syntyy `subarray`-view + uusi JS Array + 12 arvon kopio. 

Ajoin tästä nopeasti pelkän JS-mikrobenchin Node 22:ssa:

```text
Array.from(subarray 12)   ~453 ns
manual [b[i], ... x12]     ~19 ns
```

Ei tietenkään sinun koneesi absoluuttinen luku, mutta ero on niin suuri, että tähän ei kannata käyttää generic readeria yhden Stripin hot pathissa. Teillä on itse asiassa jo `read_strip_from_buffer()` joka lukee 12 sanaa suoraan array literaliin. 

Eli **pelkkä yhden Stripin tuloksen palautus voi tällä hetkellä maksaa helposti merkittävän osan koko insertin tavoitebudjetista**.

3. **Yksi insert tekee tarpeettoman ylimääräisen WASM-kutsun ennen varsinaista updatea.** TS tekee ensin:

```ts
get_projection_frame_count(state[0])
```

vain päätelläkseen onko kyse tail-insertistä, ja vasta sitten:

```ts
update_sequence(...)
```



Native tietää jo `projector.projection_frame_count`:n. Eli julkista TS-signaturea muuttamatta native update voisi hyväksyä insertion boundaryn myös `projection_frame_count` kohdalla ja ratkaista tail-semanticsin itse. Silloin **yksi WASM roundtrip pois jokaisesta insertistä**.

4. **Yhden Stripin staging on raskas O(1).** `stage_strip()` tekee yhdelle Stripille **17 erillistä vector `push_back`ia**, minkä jälkeen containment-table tekee vielä oman Entry-appendinsa. 

Raw SoA-dataa syntyy noin **81 B per Strip** jo ennen containment entryä. Vakiohinta sisältää siis 17 eri vector-objektin metadata-accessia + 17 kirjoitusta + containmentin.

Pahempi ongelma on kasvuraja: koska jokaisella SoA-lanella on oma `std::vector`, yksi kapasiteetin ylitys voi tarkoittaa **läjää erillisiä reallocointeja samassa logical insertissä**. En löytänyt nykyisestä hot pathista yhteistä `reserve`-strategiaa. Tämä selittää erityisen hyvin satojen mikrosekuntien/millisekuntien yksittäisiä piikkejä, vaikka amortized complexity on O(1).

5. **Yksi logical insert voi tehdä vielä toiset lähes 17 push_backia splitin takia.** Esimerkiksi `insert_before`, kun offset on 0 ja containing Stripillä on sisältöä, tekee:

```cpp
split_strip(projector, containing_strip_index, 0)
```



Ja `split_strip()` rakentaa uuden fragmentin taas käytännössä kaikkien samojen SoA-vectorien kautta. 

Eli yksi käyttäjän Strip ei välttämättä ole runtime-työnä "lisää yksi Strip", vaan käytännössä:

```text
stage incoming
  ~17 pushes

split source
  ~17 pushes

link both
containment update
jump maintenance
position recovery
```

Tämä alkaa jo selittää miksi public insert voi olla useita µs vaikka itse projector-walk olisi nopea.

6. **Update ratkaisee position uudelleen insertion jälkeen.** `update_projection()` tietää ennen muutosta operation indexin ja löytää containing Stripin/Gaten. Sitten se tekee `apply_insert()`, mutta tämän jälkeen kutsutaan:

```cpp
find_projection_frame_index_of(
    projector,
    incoming_strip_index,
    frame_count_diff,
    strip_count_diff)
```



Tuo tekee kahdensuuntaista jump-anchor-hakua ja jump maintenancea. Kaikissa tapauksissa sitä ei varmasti voi vain poistaa, koska sibling ordering voi muuttaa todellista paikkaa, mutta **local update pathille kannattaa ehdottomasti katsoa voiko `apply_insert/insert_between` palauttaa myös uuden Stripin lopullisen Projection-position suoraan**. Nyt ensin suoritetaan tunnetusta positiosta operaatio ja sen jälkeen tehdään erillinen position reconstruction.

### Find

Findissä en näe vastaavaa katastrofia. Public path on oikeasti hyvin pieni:

```text
JS find
→ one WASM call
→ find_strip_index_of()
→ footage_frame_index_of[gate] + offset
→ JS array lookup
```



**Gate hitissä ei ole allokaatiota.** `find_strip_index_of()` palauttaa heti, jos requested frame on nykyisessä Gate Stripissä. 

Gate mississä tulee sitten vakiohintana muun muassa:

```cpp
std::sqrt(projector.materialized_strip_count)
```

sekä jumpien tarkistusta ja jopa jump-rakenteen mutatointia findin aikana. 

Mutta yhden Stripin / Gate-hit findissä nykyinen C++ ei sisällä mitään, mikä uskottavasti oikeuttaisi **monen mikrosekunnin** hinnan. Siinä tapauksessa katsoisin ensimmäisenä JS↔WASM-boundarya ja benchmarkin single-call-mittausta, en Projector-algoritmia. Nykyinen lifecycle-bench kellottaa jokaisen operation erikseen kahdella `process.hrtime.bigint()`-kutsulla. 

### Järjestys jossa korjaisin

**#1 ehdottomasti:** älä vapauta `projection_buffer` capacitya jokaisen updaten jälkeen.

**#2:** yhden Stripin fixed native result buffer + manual 12-word JS read, pois `Array.from(subarray())`.

**#3:** tail-detection nativeen → yksi WASM call pois.

**#4:** reserve/growth strategy kaikille Projectorin SoA-arrayille yhdessä, jotta yhden logical Stripin lisäys ei laukaise 17 allocator-operaatiota.

**#5:** benchmarkkaa erikseen `stage_strip`, `split_strip`, `apply_insert`, `find_projection_frame_index_of` samalla nykyisellä Projectorilla. Veikkaan että tämän jälkeen nähdään aika suoraan mihin loput 2–5 µs update-hinnasta katoavat.

Nykyisestä koodista **projection bufferin allocate/free joka ikisellä updatella on selvin konkreettinen regression-tason suorituskykyvika**. Se kannattaa korjata ennen mitään algoritmin säätämistä.
